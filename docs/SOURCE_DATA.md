# Данные Kufar

## Источник и даты

Поиск: `GET https://api.kufar.by/search-api/v1/search/rendered-paginated`
с `cat=1010`, `typ=let`, регионом `rgn`, городом `ar`, `size=30`, `lang=ru`.
Следующая страница берётся из `pagination.pages[label=next].token`.
Детальная карточка: `GET https://api.kufar.by/search-api/v1/ads/{ad_id}/rendered?lang=ru`.
Данные карточки находятся внутри `result`, а не в корне ответа.

`list_time` сохраняется как timezone-aware UTC и определяет порядок выдачи в боте
и админке: от новых к старым, затем ID по убыванию. В интерфейсе время показывается
в `DISPLAY_TIMEZONE` (по умолчанию Europe/Minsk). Фильтр дат в админке использует
календарные дни этой зоны. Объявления без корректной даты идут в конце.

Это **время, переданное Kufar**, а не доказанная дата первой публикации или
последнего редактирования. Первое полученное значение хранится отдельно в
`first_list_time`; последующие изменения видны в истории. `created_at` — первое
обнаружение нашим сервисом, `updated_at` — техническое обновление записи,
`content_changed_at` — момент наблюдения изменения содержимого,
`last_seen_at` — время присутствия в поиске. `source_observed_at` защищает от
запоздавшего перезаписывания свежих данных старым ответом; `details_fetched_at`
фиксирует получение полной карточки. Даты из прошлого не восстанавливаются
из времени загрузки. Нет даты, дата без часового пояса, ошибка формата или дата
более чем на пять минут в будущем дают предупреждение в `data_warnings`.

## Какие данные сохраняем

| Данные | Представление |
| --- | --- |
| Заголовок, полное описание, ссылка, все фотографии | Поля карточки; описание из `result.body` сохраняет переносы строк |
| Цены BYN, USD, EUR | Decimal/Numeric с точностью до копейки, исходные суммы в минимальных единицах также остаются в JSON |
| Площадь общая, жилая, кухня | Отдельные числовые поля |
| Комнаты, этаж, этажность, год постройки | Отдельные поля |
| Ремонт, тип дома, санузел, балкон, предоплата | Подписи источника; код и исходная подпись сохраняются вместе |
| Мебель, техника, удобства, окна, инфраструктура и другие характеристики | Полный набор `ad_parameters` с `p`, `v`, `pl`, `vl`, `pu`, `g` и неизвестными полями |
| Адрес, данные аккаунта | Отдельный адрес и полный набор `account_parameters` |
| Координаты, расстояние до центра | Значения Kufar, без геокодирования и вычисления своих расстояний |
| Признак компании, ID аккаунта и списка, категория, тип, валюта | Отдельные поля; частное объявление не означает подтверждённого собственника |
| Остальные и будущие поля API | Последние полные исходные ответы `raw_search` и `raw_detail` |

`parameter_details` разделяет параметры объявления и аккаунта, сохраняет типы
значений (включая массивы и bool), подписи, единицы и группы. Плоский `parameters`
оставлен для совместимости. Нормализованные площади имеют два знака после запятой,
расстояние — три, координаты — восемь; исходная точность всегда остаётся в JSON.
Неизвестные поля API не отбрасываются. В админке доступны оба JSON и все параметры.
Телефон API может скрывать; отсутствие телефона нельзя исправить парсером.

Сохраняются последние снимки, а не каждый HTTP-ответ навсегда. `listing_changes`
хранит обнаружение, фактические изменения полей со значениями до/после,
снятие источником и ручное скрытие/восстановление. Повторный неизменившийся скрейп
не создаёт новую запись истории. Отображаются последние 50 событий объявления.
Ошибка загрузки деталей не стирает уже полученное полное описание и параметры.
Поиск может маскировать `account_id` нулём; такой ответ не затирает ID аккаунта,
полученный из детальной карточки.

## Обход каталога

Быстрый поиск читает заданное количество последних страниц, включая уже известные
объявления. В админке Tasks независимо настраиваются интервал в минутах и число
страниц за запуск. Достижение этого числа — успешное завершение быстрого поиска,
а не повод запускать полный обход. Первый быстрый запуск также соблюдает бюджет.
Обновляются новые и известные объявления, `list_time`, содержимое и при необходимости
детали. Быстрый поиск не архивирует отсутствующие объявления.

Полный рефреш имеет отдельные интервал в минутах и переключатель в Tasks.
Он проходит все страницы и обновляет детали, включая изменения текста без сдвига
`list_time`. По умолчанию `FULL_RECONCILIATION_MAX_PAGES=0`; положительный аварийный
предел делает обход незавершённым и запрещает архивирование. Ошибки поиска,
некорректная пагинация, повтор курсора и ошибки сохранения также запрещают
архивирование; полученные записи при этом сохраняются.

Расписания и бюджет быстрого поиска хранятся в БД. Значения
`NEW_LISTINGS_DEFAULT_INTERVAL_SECONDS`, `NEW_LISTINGS_MAX_PAGES` и
`FULL_RECONCILIATION_INTERVAL_SECONDS` задают начальные настройки, а последующие
перезапуски не перезаписывают сохранённые параметры. Ожидающий или выполняющийся
запуск того же режима не ставится планировщиком повторно. Два процесса скрейпера
позволяют выполнять быстрый поиск параллельно долгому полному обходу.

## Уведомления

Текущая доставка — отдельная карточка на каждую квартиру; подробности в
[BOT_SEARCH.md](BOT_SEARCH.md).


Изменение известного ID, включая новое `list_time`, обновляет карточку и её место
в выдаче **без повторного уведомления**. Новизна определяется первым обнаружением
ID после курсора пользователя; `list_time` дополнительно должно попадать в период
его наблюдения. Поэтому загрузка исторического каталога не рассылает старые
объявления как новые, а поздно пришедшая в поиск свежая квартира не теряется.
Без корректного `list_time` карточка доступна в просмотре, но не включается
в автоматическую ленту новых совпадений. Уведомления и сохранение используют транзакционную
блокировку каталога, чтобы параллельный скрейп не оставил запись за уже
продвинутым курсором. Статусы просмотра, избранное и ручной архив сохраняются.

## Обновление существующей установки

Миграция `20261015_0005` сохраняет существующие строки и пользовательские настройки,
добавляет nullable-даты и JSON, переводит цены в Numeric и ставит полную сверку
на ближайший запуск. Утерянные старым integer-парсером копейки и отсутствующие
даты заполнятся только после повторного получения объявления от источника.
Перед миграцией нужна резервная копия; порядок обновления описан в
[COMPOSE.md](COMPOSE.md). Downgrade удаляет новые метаданные и историю,
а дробные цены обрезает, поэтому восстановление старой версии требует backup.
